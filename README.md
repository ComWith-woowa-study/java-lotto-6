# 로또
**<MVC 패턴 도입>**

입력 재시도와 숫자에 관한 여러 규칙들, 출력 포맷도 복잡하기 때문에 임의로 설계하기 복잡하다고 생각해서 관심사 분리를 위해 MVC 패턴을 도입하기로 결정했다. MVC 패턴을 사용하게 되면 입력과 출력이 바뀐다고 해도 규칙에는 전혀 영향을 주지 않고, 무엇보다 Model만 떼어내서 검증이 가능하기 때문에 단위 테스트 작성에도 유리하다. 무엇보다 역할이 깔끔하게 분리되기 때문에 가독성이 좋다. 규칙이 바뀌면 Model만, 입력 및 출력 문구가 바뀌면 View만, 프로그램 흐름이 바뀌면 Controller와 Service를 손보면 된다. 파일마다 하나의 책임만을 담당하게 함으로써 SRP 원칙을 만족시켜 코드가 깔끔해진다.

&nbsp;

**<기능 요구사항>**

1. 1장에 1000원인 로또를 1000원 단위로 구매한다.
2. 로또 번호의 숫자 범위는 1~45까지이고, 보너스 번호 1개를 입력받는다. (중복 불가)
3. 당첨 번호와 비교해서 당첨 내역(등수 및 상금) 및 수익률을 계산한다.

&nbsp;

**<역할과 경계>**
- `Model`: 필요한 속성과 규칙을 계산한다.
- `Controller`: 입력을 받고, 유스케이스를 실행하고, 결과를 전달한다.
- `View`: 컨트롤러부터 결과를 받아서 표현한다.

&nbsp;

**<설계>**

- `Model(명사)`: 1000원, 로또 번호, 보너스 번호, 당첨 번호, 등수, 상금, 수익률 

1. `Money`: 구매 금액
2. `Lotto`: 로또
3. `Lottos`: 로또 묶음(등수를 카운트하거나 총상금을 응집하기 위해)
4. `WinningNumbers`: 당첨 번호
5. `Rank`: 등수
6. `Statistics`: 결과

&nbsp;

- `Service`: 비즈니스 로직(로또를 구매한다, 결과를 평가한다)
- `View`: 입력 프롬포트, 출력 형식
- `Controller`: 구매 금액을 입력 받는다 -> 금액만큼 로또를 구매한다 -> 당첨 번호를 입력 받는다 -> 결과를 출력한다


<아쉬웠던 점 & 고민했던 부분>
1. `List<Lotto>`가 아닌 굳이 Lottos 모델을 추가해야 하는지 고민했다. 하지만 당첨 번호와의 협업에서 일일이 구매한 만큼의 Lotto 인스턴스를 생성하게 된다면 코드가 길어질 것 같았다. 또한 Service에서도 전체 로또를 가져와 흐름을 쉽게 가져갈 수 있었다.
2. 굳이 숫자 생성기를 인터페이스로 뽑아내야 하는지 의문이었다. 하지만 인터페이스로 뽑아내야 테스트가 쉬워지고, 상위 수준 모듈은 구현체에 의존하지 않고 추상에 의존해야 한다는 DIP 원칙을 지킬 수 있다. 추가로 향후 다른 숫자 생성 전략이 추가된다면 단순히 구현체만 추가하면 되기 때문에 OCP 원칙도 지킬 수 있다.
3. MIN, MAX 등과 같은 클래스 상수로 여러 코드에 두는게 맞는건지 의문이다. 개선이 필요해보인다.
4. `ResultResponse` DTO를 꼭 추가해야 하나 고민했다. 하지만, 현재 View가 필요로 하는 건 등수별 횟수와 수익률을 반환하는 것이기 때문에 좀 더 간단히 그릴 수 있도록 도움을 줄 수 있다.
